# Architecture

How every feature is layered, the rules the stores share, and the live sync. Part of the rules for the code; [`README.md`](./README.md) lists the others.

## Layers

Each feature is split the same way, and new features should follow it:

1. **`composables/*-actions.ts`**: all Supabase calls, as plain functions that take a `SupabaseClient` as a parameter. No Nuxt imports, so they are unit tested with a fake client.
2. **`stores/*.ts`** (Pinia options stores): thin. They call `useSupabaseClient()`/`useSupabaseUser()`, delegate to the actions, and hold state.
3. **`utils/*.ts`**: pure reducers and helpers for state transitions that need testing on their own.
4. **Components and pages**: rendering only.

A composable with logic worth testing is split in two: a plain function in one file and a thin `use-*.ts` wrapper that supplies the Nuxt runtime (`household-realtime.ts` ← `use-household-realtime.ts`).

## Shared list logic

To-dos and shopping share one implementation of the hard part. `utils/list-state.ts` is generic over `ListItem` (`types/list.ts`: `id`, `list_id`, `position`, `deleted_at`) and holds the rules for optimistic adds, dedup, soft delete, Realtime events and resync. Only the actions, the store, the components and list-specific ordering (`utils/shopping-state.ts`: checked items sink to the bottom) exist per list. `stores/todos.ts` and `stores/shopping.ts` are deliberately parallel; a fix in one usually belongs in the other.

Whiteboard strokes (`stores/whiteboard.ts`) follow the same rules without being list items: the reducers that need only `id` and `deleted_at` are typed over `SyncedRow` (`types/synced-row.ts`) and shared, and `utils/whiteboard-state.ts` holds what differs. A fix to those rules usually belongs in all three stores.

Recipes (`stores/recipes.ts`) are the fourth store on those rules, with `utils/recipe-state.ts` for what differs, and a fix usually belongs there too. They differ in two ways. Recipes hang on the household without a list or board row, so `householdId`, set once they are loaded, is what events and resync wait for. And a recipe can be edited: a new one is saved before it enters state (the form waits for it, so there is no `inserts-in-flight`), and an edit is optimistic and sends only the fields that changed (`utils/recipe-draft.ts`).

Vacations (`stores/vacations.ts`) are the fifth store on those rules, with `utils/vacation-state.ts` for what differs, and a fix usually belongs there too. It is one store for three tables, `vacations`, `vacation_tasks` and `vacation_people`, with one of each piece of bookkeeping for all: the pieces are keyed by a row's id. Like recipes, the rows hang on the household, and a new vacation is saved before it enters state: the function `create_vacation` (0015) writes it with its tasks in one transaction: none, or copies of an earlier vacation's (`tasksToCopy`), open and nobody's. A task is added optimistically, as a list item is. What a page shows depends on the day, and every function that does takes the day as a parameter (`utils/local-date.ts`); a calendar day is a `YYYY-MM-DD` string and never goes through `new Date("2026-12-05")`, which is midnight in UTC. A person taken off a trip stays as a row, and whose a task is, is worked out from that row by `assigneeOf` (`utils/vacation-share.ts`), never written to the tasks. A trip has no meals of its own: its meals are the meal plan's entries on its days, shown at `/meals?trip=<id>`, and the vacation page's "Meals" row only links there and counts the dinners (`dinnersPlannedLine`). The table `vacation_meals` (0017) and its page were removed with slice 1b of the meal planner; migration 0020 drops it. The kind of stay is a label that may be edited and decides nothing. The feature is built in slices; `docs/features/vacations/slice-1.md`, `slice-2.md` and `slice-3.md` are the three (slice 3's meals are overtaken, see the meal plan), and the folder's `README.md` lists all its files.

The meal plan (`stores/meal-plan.ts`) is the sixth store on those rules, with `utils/meal-plan-state.ts` for what differs, and a fix usually belongs there too. An entry (`meal_plan_entries`, 0018) is a recipe or a title on a day and in a slot; a trip's meals are the entries on its days (`/meals?trip=<id>`, `MealTripView`), and `vacation_meals` is gone. The store holds date ranges, not the table: `load(householdId, range)` fetches a range the first time and `resync()` fetches every range held and keeps the rows outside them (`mergeMealPlanResync`). An edit (`update`, `move`, `makeRecipeOf`) is optimistic and reverts only the columns it changed; `makeRecipeOf` is sent even for an entry that is not in state, because the recipe form may have been reloaded. The shopping run from the plan (`planShoppingRun`, `utils/shopping-run.ts`, then `putMealsOnShoppingList` in `composables/meals-on-shopping-list.ts`) goes entry by entry, because `addAll` says only how many items it saved. A removal is held for 5 seconds for "Undo" (`holdRemoval`) and sent at once when the member leaves the page or removes another entry; a closed tab sends nothing. `utils/meal-week.ts` holds the weeks (from Monday), the 17:00 switch and the dashboard's window, and `utils/dinner-order.ts` the order in which the Tonight tile proposes recipes. Proposals go through the `MealSuggester` interface (`utils/meal-suggester.ts`, implemented by `repertoireSuggester`), for the Tonight tile and for "Fill my week" on the week page alike; replace that object, not the callers, to propose differently. "Fill my week" (`composables/use-week-fill.ts`, rules in `utils/week-fill.ts`) holds its proposal on the device, in the page, until "Plan these" adds each dinner with `add`: an unplanned proposal must neither reach the other members nor count in `count_planned_dinner_days`. The feature is built in slices; `docs/features/meal-planner/README.md` lists the files that hold them.

The kids (`stores/kids.ts`) are the seventh store on those rules, with `utils/kids-state.ts` for what differs, and a fix usually belongs there too. It is one store for two tables, `household_children` and `meal_reactions` (0021), like the vacation store, whose row reducers it reuses. A child is no user: a name on the household, drawn as letters on a disc (`<person-avatar>`), never sent to Gravatar, and never named in a notice. Only exceptions are stored: "ate it" is no live row; a change between picked at and refused updates the live row, going back to "ate it" soft-deletes it, and recording again inserts a new row (the unique index on entry and child covers live rows only). The record (`/kids`) and the Tonight order (`dinnerSuggestionOrder` takes a `demoted` set, see `refusalsByRecipe`) count over the meal plan's entries that the page already holds, the 8 weeks of the lookback; there is no join.

Every store is loaded with `load(householdId)` (the meal plan with `load(householdId, range)`): by the dashboard, whose tiles and roster show all seven, and by the feature's own pages. Only the first call fetches everything behind a spinner; later ones merge in the background (`resync()`), because replacing state would drop a write that is still on its way. In the three older stores the first fetch is `init()`, which replaces state; nothing but `load()` may call it, and a `load()` during it waits for it (the recipe store and the vacation store fetch a second time instead).

The rules the reducers and stores encode:

- **Client-generated ids.** An add creates the row locally under `crypto.randomUUID()` and inserts it with that id, so the server-confirmed row and the Realtime echo upsert instead of duplicating.
- **Soft deletes only.** `deleted_at` is set, the row stays in state as a tombstone, and getters filter it out. Nothing may undo a local soft delete. Newer tables (0012, 0014) don't grant `delete` to `authenticated` at all.
- **`position` is a fractional numeric** for reordering without reindexing (`utils/position.ts`).
- **`household_id` is denormalized onto every item table** so RLS policies and Realtime filters need no join.

Three pieces of bookkeeping live at module level in each store, outside Pinia state, because they are not renderable state:

- `utils/inserts-in-flight.ts`: a check or remove waits for the item's insert, otherwise its UPDATE reaches the server first and matches no row.
- `utils/changes-during-fetch.ts`: ids changed while a resync fetch is in flight keep their local version, as do `pendingIds`.
- `utils/realtime-event-order.ts`: Realtime does not deliver a row's events in commit order, so an event with an older `commit_timestamp` than the newest seen for that item is dropped. There is no `updated_at` trigger; don't order by `updated_at`.

## Realtime

`subscribeToHouseholdChanges` (`composables/household-realtime.ts`) opens **one channel per household**, filtered by `household_id=eq.<id>`, and every item table adds its listeners to it (the meal plan's is `onMealPlanEntryChange`). Only INSERT and UPDATE are subscribed: DELETE events can't be filtered and bypass RLS, and the app never hard-deletes. `postgres_changes` has no replay, so every `SUBSCRIBED` (first join and each rejoin) triggers `resync()` on every list store, and so does the server's report "Subscribed to PostgreSQL" a quarter to half a second later: only from then on do changes flow, and one made in between is in no event. A store's `resync()` does nothing while its first load is running, so a load that answers after that report can still miss such a change. A new table also has to be added to the `supabase_realtime` publication (see migration 0011), or events silently never arrive.

An UPDATE event leaves out a large column the update didn't change (Postgres TOAST): a stroke's `points` is missing from its soft-delete event, and a recipe's `instructions` or `kids_version` from a rename. A reducer for a table with such a column has to lay the event over the local row instead of replacing it (`applyStrokeRealtimeEvent`, `applyRecipeRealtimeEvent`). Where such a row can also be edited, an event may tell only part of a live row that isn't in state; the store then fetches it (`recipeEventNeedsFetch`).

`layouts/default.vue` mounts this once. Order matters there: `useResetStoresOnUserChange()` runs before `useHouseholdRealtime()`, so a new user never sees the previous user's household.
